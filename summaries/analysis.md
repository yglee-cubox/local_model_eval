# 벤치마크 결과 분석: Qwen3.8-27B vs gemma-4-31B-it

2026-10-02 작성. 대상은 [README.md](README.md) 표에 있는 실행들입니다.

- **LiveCodeBench (LCB):** release_v6 전체 1055문제, 문제당 10개 생성.
- **SWE-bench Pro V2:** HARD-51, 모델당 1회 실행.

Qwen3-1.7B 는 설정이 달라서 (LCB n=1, SWE-bench Pro 는 환경 수정 전 실행) 참고로만 적었습니다.

2. **에이전트 작업 (SWE-bench Pro) 은 Qwen 이 압도적입니다.** 27개 대 8개로, thinking 설정이 아니라 에이전트로 일하는 방식의 차이입니다 (2장).
   gemma 는 코드를 고친 뒤 테스트로 확인하지 않고 바로 제출하고, Qwen 은 테스트를 반복하며 고칩니다.

3. **thinking 을 끄면 두 벤치마크 모두 떨어집니다.** 떨어지는 폭은 모델과 벤치마크마다 다릅니다.
   - LCB: Qwen 은 −13.8%p 로 크게 떨어지고, gemma 는 −5.2%p 입니다.
   - SWE-bench Pro: 두 모델 모두 3~4개 줄어드는 정도입니다.

## 2. SWE-bench Pro

**질문.** 둘 다 thinking 을 켰는데 Qwen3.8-27B 는 27/51, gemma-4-31B-it 는 8/51 입니다. 왜 이렇게 차이가 날까요?

**결론.** thinking 설정 때문이 아닙니다. 두 모델이 **에이전트로 일하는 방식**이 다릅니다.

### 2-1. thinking 의 효과는 두 모델이 비슷합니다

| 모델 | thinking 끔 | thinking 켬 | 차이 |
|---|---|---|---|
| gemma-4-31B-it | 5/51 (9.8%) | 8/51 (15.7%) | +3 |
| Qwen3.8-27B | 23/51 (45.1%) | 27/51 (52.9%) | +4 |

thinking 을 끈 Qwen (23개) 이 thinking 을 켠 gemma (8개) 보다 훨씬 높습니다. 차이의 대부분은 모델 자체에서 나옵니다.
1장에서 봤듯 코드를 짜는 능력은 비슷하니, 저장소를 탐색하고 수정하고 검증하는 에이전트 작업에서 갈리는 것입니다.

- **gemma** 의 실패는 대부분 둘 중 하나입니다. 목표 테스트를 아예 못 맞추거나, 파일을 통째로 다시 쓰다가 원래 되던 기능을 망가뜨립니다.

- **Qwen (thinking 끔)** 은 시간은 충분했지만 9개가 250스텝을 다 쓰고 끝났습니다 (LimitsExceeded).
  해결 못 한 인스턴스에서 호출 125.7회, 테스트 29.2회로, 고치지 못한 채 테스트를 계속 반복한 경우가 많습니다.

### 2-4. 소스 파일을 통째로 덮어쓰는 이유

> 2026-10-02 정정: 이 문서의 첫 버전에는 "heredoc 으로 소스 파일을 덮어쓴 인스턴스 gemma 46/51, Qwen 22/51",
> "제출 직전 마지막 행동이 덮어쓰기 21/51 대 1/51" 이 있었습니다.
> 이 숫자는 새로 만든 파일과 재현 스크립트를 수정 대상 파일과 섞어 센 것이었습니다.
> 기존 소스 파일만 다시 세면 덮어쓴 인스턴스는 **gemma 30/51, Qwen 27/51 로 비슷합니다.** 2-2 표도 다시 센 값으로 바꿨습니다.

덮어쓰기 자체는 두 모델 모두 합니다. 차이는 **무엇을 보고 덮어쓰는지** 와 **덮어쓴 뒤 확인하는지** 에 있습니다.

**1) 공통 원인: 설정에 여러 줄 편집 도구가 없습니다.**

공식 설정 (`mini_textbased.yaml`) 의 프롬프트는 편집 예시를 두 가지만 보여줍니다.
- 새 파일 만들기: `cat <<'EOF' > newfile.py`
- 한 줄 치환: `sed -i 's/old/new/'`

여러 줄을 고치는 도구가 없어서, 함수 하나를 바꾸려 해도 "새 파일 만들기" 예시를 기존 파일에 그대로 쓰게 됩니다.
실제 편집 방법은 다음과 같습니다 (thinking 켬, 인스턴스당 평균).

| 편집 방법 | gemma | Qwen |
|---|---|---|
| `sed -i` | 2.1 | 2.1 |
| 기존 소스를 heredoc 으로 덮어쓰기 | 1.2 | 2.3 |
| Python 으로 문자열 찾아 바꾸기 (`python3 - <<EOF ... .replace(...)`) | **0.1** | **5.1** |

Qwen 은 프롬프트에 없는 세 번째 방법을 스스로 씁니다. Python 으로 파일을 읽어 필요한 부분만 바꾸는 방식이라 정확합니다.
gemma 는 이 방법을 거의 쓰지 않고 `sed` 와 덮어쓰기에 의존합니다.

**2) gemma 만의 문제: 잘린 출력을 보고 파일 전체를 다시 씁니다.**

이 설정은 명령 출력이 **10000자를 넘으면 앞 5000자와 뒤 5000자만 보여주고 중간을 생략** 합니다.
큰 파일을 `cat` 으로 열면 중간이 보이지 않습니다.

| | gemma 켬 | Qwen 켬 | gemma 끔 | Qwen 끔 |
|---|---|---|---|---|
| 파일 전체 읽기 (`cat`, `nl -ba`) 중 출력이 잘린 비율 | 64/167 | 50/138 | 48/105 | 32/76 |
| **잘린 파일을 그대로 덮어쓴 횟수** | **16** | **0** | **16** | **0** |
| 그 결과 최종 패치에서 원래 줄이 100줄 넘게 사라진 파일 | 6 | 0 | 5 | 0 |

- 두 모델 모두 잘린 출력을 자주 받습니다.
- **Qwen** 은 잘린 출력을 받으면 `sed -n '1200,1300p'` 처럼 필요한 구간을 나눠 읽고, 그 부분만 고칩니다. 잘린 파일을 덮어쓴 적이 없습니다.
- **gemma** 는 앞뒤 5000자와 몇 개 구간만 본 상태에서 파일 전체를 기억으로 다시 씁니다. 보지 못한 중간 코드는 사라집니다.

실제 사례입니다 (gemma, thinking 켬).

| 인스턴스 | 파일 | 원래 줄 삭제 / 새로 씀 |
|---|---|---|
| openlibrary-322d7a46 | `openlibrary/solr/update_work.py` | 1399 / 189 |
| openlibrary-630221ab | `openlibrary/core/bookshelves.py` | 484 / 16 |
| tutanota-f373ac38 | `src/api/worker/crypto/CryptoFacade.ts` | 466 / 55 |

`update_work.py` 는 이런 순서였습니다.
1. `cat` 으로 열었지만 출력이 잘려 앞뒤만 봤습니다.
2. 몇 구간을 `sed -n` 으로 더 본 뒤 185줄로 다시 썼습니다.
3. `git restore` 로 되돌렸습니다.
4. 다시 418줄로 덮어썼습니다.

두 번째로 쓴 파일에는 `# Keep existing helpers and main`, `# ... other fields ...` 같은 주석이 실제 코드 대신 들어 있었습니다.
원래 코드를 "그대로 둔다" 고 주석만 쓰고 내용은 지운 것입니다.

잘린 파일을 덮어쓴 인스턴스의 결과는 다음과 같습니다.
- gemma 켬: 14개 중 1개 해결, 7개는 기존 테스트까지 깨뜨림 (깨진 인스턴스는 평균적으로 기존 테스트의 38% 실패)
- gemma 끔: 16개 중 1개 해결, 8개는 기존 테스트까지 깨뜨림

**3) gemma 는 덮어쓴 뒤 확인하지 않습니다.**

| 다음 행동 | gemma 켬 (60회) | Qwen 켬 (50회) |
|---|---|---|
| 테스트·컴파일·실행으로 검증 | 12 | 27 |
| 다른 파일 수정 | 22 | 8 |
| 읽기 등 | 15 | 15 |
| 바로 제출 | **11** | **0** |

**4) 덮어쓰기 자체가 문제는 아닙니다.**

최종 패치에서 덮어쓴 파일이 남은 인스턴스만 보면 다음과 같습니다.
- Qwen: 12개 중 8개 해결, 기존 테스트를 깨뜨린 것 2개
- gemma: 27개 중 5개 해결, 기존 테스트를 깨뜨린 것 11개

덮어쓴 파일에서 원래 줄이 지워진 수는 gemma 가 평균 98줄, 다른 방법으로 고친 파일은 12줄입니다.

**정리**

| 원인 | 해당 모델 |
|---|---|
| 설정에 여러 줄 편집 도구가 없어 heredoc 덮어쓰기를 편집 수단으로 씀 | 둘 다 |
| Python 치환 같은 정확한 편집 방법을 스스로 찾지 못함 | gemma |
| 잘린 출력을 보고 파일 전체를 다시 써서 보지 못한 코드를 지움 | gemma |
| 덮어쓴 뒤 검증하지 않고 넘어가거나 제출함 | gemma |

문제는 다 읽지 않은 파일을 덮어쓰고, 그 뒤에 확인하지 않는 것입니다.

### 2-5. 원인 정리

1. **모델이 학습된 방향이 다릅니다.**
   - Qwen3.8-27B 는 모델 카드에서 SWE-bench Pro 등 에이전트 코딩 벤치마크를 내세우는 모델입니다. 탐색 → 수정 → 테스트 → 수정을 길게 반복하도록 학습된 것으로 보입니다.
   - gemma-4-31B-it 는 범용 instruct 모델입니다. 적은 단계에서 결론을 내고 제출하는 경향이 있습니다.
2. **같은 "thinking 켬" 이어도 생각의 양이 다릅니다.**
   Qwen 은 길게 생각하면서 다음 검증 단계를 계획하고, gemma 는 응답의 60% 에서 thinking 을 건너뛰고 바로 행동합니다.
3. **gemma 는 파일 편집이 거칩니다 (2-4).**
   출력이 잘려 일부만 본 파일을 통째로 다시 써서 원래 코드를 지우고, 덮어쓴 뒤 확인하지 않습니다.
   기존 테스트를 깨뜨린 실패 (16개) 의 상당수가 여기서 나옵니다.
4. **설정이나 환경 문제는 아닌 것으로 봅니다.**
   - 두 실행 모두 같은 에이전트 설정 (`mini_textbased.yaml`, 250스텝, 3000초) 을 썼습니다.
   - 응답이 길이 제한으로 잘린 경우 (`finish_reason=length`) 는 4개 실행 모두 0건입니다.
   - gemma 는 제한 시간에 걸린 인스턴스가 없습니다. 시간이 모자라서 진 것이 아닙니다.
   - 컨테이너 PATH 문제를 고치기 전 (`agent_in_container.py` 의 `load_image_env`) 환경에서 일부 인스턴스가 돈 쪽은 오히려 Qwen 입니다. 그래도 Qwen 이 높습니다.

**Qwen3-1.7B (0/51) 참고.** 17개가 `ContextWindowExceededError` 로 끝났습니다.
작은 모델이 컨텍스트를 다 써 버린 경우이고, 나머지도 형식 오류나 스텝 초과입니다.
이 실행은 PATH 수정 전에 돌아서 다른 실행과 조건이 같지 않습니다.

## 3. 해석할 때 주의할 점

- **LCB 설정이 실행마다 다릅니다.** 샘플링과 max_tokens 가 다르니 (1-1), 특히 thinking 끔끼리의 비교 (gemma 0.823 vs Qwen 0.724) 는 조심해서 보세요.
  - gemma 끔은 temp 0.2 로 거의 결정적으로 생성했습니다.
  - Qwen 끔은 temp 0.7 에 presence_penalty 1.5 입니다.
- **SWE-bench Pro 는 모델당 51개를 1번씩만 돌렸습니다.** 몇 %p 정도는 흔들릴 수 있습니다. 다만 27개 대 8개는 그 범위를 훨씬 넘습니다.
- **SWE-bench Pro 는 공식 프로토콜이 아닙니다.** 에이전트 컨테이너에서 네트워크와 `/purestorage` 에 접근할 수 있으니 체크포인트끼리 비교하는 용도로만 쓰세요.
- **모델 카드 점수와는 직접 비교하기 어렵습니다.** LCB 문제 구간과 SWE-bench Pro 하네스가 다릅니다.
- **SWE-bench Pro 의 행동 분류는 근사치입니다.** 테스트 실행, 파일 덮어쓰기 등은 에이전트가 실행한 명령을 정규식으로 분류했습니다.
  - 테스트로 센 명령: `pytest`, `go test`, `npm test`, `jest`, `mocha`, `yarn test`, `unittest`, `tox`
  - 직접 만든 재현 스크립트 실행 (`python repro.py` 등) 은 테스트로 세지 않았습니다.
  - 덮어쓰기: `cat <<EOF > 파일` 또는 `cat > 파일 <<EOF` 중 대상이 소스 확장자 (py, js, jsx, ts, tsx, go) 이고,
    최종 패치에서 새 파일이 아니며, 경로에 repro, test, debug 같은 단어가 없는 경우만 셌습니다.
  - 출력 잘림: 파일 전체 읽기 (`cat 파일`, `nl -ba 파일`) 의 결과에 `<elided_chars>` 가 있는 경우입니다.
