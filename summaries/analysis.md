# 벤치마크 결과 분석: Qwen3.8-27B vs gemma-4-31B-it

2026-10-02 작성. 대상은 [README.md](README.md) 표에 있는 실행들입니다.

- **LiveCodeBench (LCB):** release_v6 전체 1055문제, 문제당 10개 생성.
- **SWE-bench Pro V2:** HARD-51, 모델당 1회 실행.

Qwen3-1.7B 는 설정이 달라서 (LCB n=1, SWE-bench Pro 는 환경 수정 전 실행) 참고로만 적었습니다.

## 요약

| 모델 | thinking | LCB pass@1 | LCB hard | SWE-bench Pro |
|---|---|---|---|---|
| gemma-4-31B-it | 켬 | **0.875** | 0.711 | 8/51 (15.7%) |
| gemma-4-31B-it | 끔 | 0.823 | 0.597 | 5/51 (9.8%) |
| Qwen3.8-27B | 켬 | 0.862 | 0.692 | **27/51 (52.9%)** |
| Qwen3.8-27B | 끔 | 0.724 | 0.508 | 23/51 (45.1%) |
| Qwen3-1.7B | 켬 | 0.523 (n=1) | 0.140 | 0/51 |

1. **코드 생성 (LCB) 은 두 모델이 비슷합니다.** thinking 켬 기준 gemma 0.875, Qwen 0.862 입니다.
   Qwen 은 생성 길이 제한 (65536 토큰) 에 걸린 답이 6% 있어서, 이 차이는 모델 능력보다 설정 영향이 큽니다 (1-3).
2. **에이전트 작업 (SWE-bench Pro) 은 Qwen 이 압도적입니다.** 27개 대 8개로, thinking 설정이 아니라 에이전트로 일하는 방식의 차이입니다 (2장).
   gemma 는 코드를 고친 뒤 테스트로 확인하지 않고 바로 제출하고, Qwen 은 테스트를 반복하며 고칩니다.
3. **thinking 을 끄면 두 벤치마크 모두 떨어집니다.** 떨어지는 폭은 모델과 벤치마크마다 다릅니다.
   - LCB: Qwen 은 −13.8%p 로 크게 떨어지고, gemma 는 −5.2%p 입니다.
   - SWE-bench Pro: 두 모델 모두 3~4개 줄어드는 정도입니다.

## 2. SWE-bench Pro

**질문.** 둘 다 thinking 을 켰는데 Qwen3.8-27B 는 27/51, gemma-4-31B-it 는 8/51 입니다. 왜 이렇게 차이가 날까요?

**결론.** thinking 설정 때문이 아닙니다. 두 모델이 **에이전트로 일하는 방식**이 다릅니다.

### 2-1. thinking 의 효과는 두 모델이 비슷합니다

| 모델 | thinking 끔 | thinking 켬 | 차이 |
|---|---|---|---|
| gemma-4-31B-it | 5/51 (9.8%) | 8/51 (15.7%) | +3 |
| Qwen3.8-27B | 23/51 (45.1%) | 27/51 (52.9%) | +4 |

thinking 을 끈 Qwen (23개) 이 thinking 을 켠 gemma (8개) 보다 훨씬 높습니다. 차이의 대부분은 모델 자체에서 나옵니다.
1장에서 봤듯 코드를 짜는 능력은 비슷하니, 저장소를 탐색하고 수정하고 검증하는 에이전트 작업에서 갈리는 것입니다.

### 2-2. 에이전트 행동 비교

인스턴스 하나당 평균입니다.

| | gemma 켬 | Qwen 켬 | gemma 끔 | Qwen 끔 |
|---|---|---|---|---|
| 모델 호출 수 | 21.2 | 84.6 | 14.5 | 98.0 |
| 호출당 생성 토큰 | 758 | 1763 | 612 | 189 |
| 호출당 thinking 길이 (글자) | 1.1k | 6.1k | - | - |
| 테스트 명령 실행 횟수 | **1.2** | **13.0** | 0.6 | 21.6 |
| 테스트를 한 번이라도 돌린 인스턴스 | **24%** | **88%** | 16% | 92% |

thinking 켬 실행만 따로 보면 다음과 같습니다.

| | gemma 켬 | Qwen 켬 |
|---|---|---|
| 제출 직전 마지막 행동이 테스트 | 5/51 | 19/51 |
| 제출 직전 마지막 행동이 소스 파일 통째로 덮어쓰기 | **21/51** | 1/51 |
| 소스 파일을 heredoc (`cat <<EOF > file`) 으로 통째로 덮어쓴 인스턴스 | 46/51 | 22/51 |
| 해결한 인스턴스의 평균 테스트 실행 | 1.9 | 15.9 |
| 해결 못 한 인스턴스의 평균 테스트 실행 | 1.1 | 9.8 |

- **gemma** 는 대략 "코드 읽기 → 파일 덮어쓰기 → 바로 제출" 순서입니다. 고친 코드가 실제로 도는지 확인하지 않고 끝내는 경우가 대부분입니다.
- **thinking 양** 도 다릅니다. gemma 는 응답 하나당 thinking 이 Qwen 의 약 1/6 입니다. 호출 수까지 곱하면 인스턴스당 생각하는 양이 약 20배 적습니다.
- thinking 을 끈 Qwen 은 짧게 답하는 대신 호출과 테스트를 더 많이 합니다 (98회, 테스트 21.6회).
  생각의 길이를 행동 횟수로 메우는 모습입니다.

### 2-3. 실패 유형

해결 못 한 인스턴스의 최종 패치를 채점 결과로 나눴습니다.
"목표 테스트" 는 `fail_to_pass`, "기존 테스트" 는 `pass_to_pass` 입니다.

| | gemma 켬 (43개) | Qwen 켬 (24개) | gemma 끔 (46개) | Qwen 끔 (28개) |
|---|---|---|---|---|
| 목표 테스트를 하나도 통과 못 함 | **25** | 4 | 22 | 5 |
| 목표 테스트 일부만 통과 | 16 | 9 | 22 | 22 |
| 목표 테스트는 다 통과했지만 기존 테스트를 깨뜨림 | 0 | 0 | 2 | 0 |
| 빈 패치 | 2 | **11** | 0 | 1 |
| (위 실패 중 기존 테스트도 깨뜨린 경우) | **16** | 2 | 11 | 5 |

- **gemma** 의 실패는 대부분 둘 중 하나입니다. 목표 테스트를 아예 못 맞추거나, 파일을 통째로 다시 쓰다가 원래 되던 기능을 망가뜨립니다.
  테스트를 거의 돌리지 않으니 이런 실수를 잡지 못합니다.
- **Qwen (thinking 켬)** 의 실패 중 11개는 빈 패치입니다.
  그중 9개는 인스턴스 제한 시간 3000초에 걸려 강제 종료되면서 패치를 저장하지 못한 경우 (`container_timeout_or_crash`) 입니다.
  나머지 TimeExceeded 7개 중 4개는 해결했습니다. 오래 작업하다 시간이 모자란 경우라, 제한 시간이 더 길었다면 점수가 오를 수 있습니다.
- **Qwen (thinking 끔)** 은 시간은 충분했지만 9개가 250스텝을 다 쓰고 끝났습니다 (LimitsExceeded).
  해결 못 한 인스턴스에서 호출 125.7회, 테스트 29.2회로, 고치지 못한 채 테스트를 계속 반복한 경우가 많습니다.

### 2-4. 원인 정리

1. **모델이 학습된 방향이 다릅니다.**
   - Qwen3.8-27B 는 모델 카드에서 SWE-bench Pro 등 에이전트 코딩 벤치마크를 내세우는 모델입니다. 탐색 → 수정 → 테스트 → 수정을 길게 반복하도록 학습된 것으로 보입니다.
   - gemma-4-31B-it 는 범용 instruct 모델입니다. 적은 단계에서 결론을 내고 제출하는 경향이 있습니다.
2. **같은 "thinking 켬" 이어도 생각의 양이 다릅니다.**
   Qwen 은 길게 생각하면서 다음 검증 단계를 계획하고, gemma 는 짧게 생각하고 바로 행동합니다.
3. **설정이나 환경 문제는 아닌 것으로 봅니다.**
   - 두 실행 모두 같은 에이전트 설정 (`mini_textbased.yaml`, 250스텝, 3000초) 을 썼습니다.
   - 응답이 길이 제한으로 잘린 경우 (`finish_reason=length`) 는 4개 실행 모두 0건입니다.
   - gemma 는 제한 시간에 걸린 인스턴스가 없습니다. 시간이 모자라서 진 것이 아닙니다.
   - 컨테이너 PATH 문제를 고치기 전 (`agent_in_container.py` 의 `load_image_env`) 환경에서 일부 인스턴스가 돈 쪽은 오히려 Qwen 입니다. 그래도 Qwen 이 높습니다.

**Qwen3-1.7B (0/51) 참고.** 17개가 `ContextWindowExceededError` 로 끝났습니다.
작은 모델이 컨텍스트를 다 써 버린 경우이고, 나머지도 형식 오류나 스텝 초과입니다.
이 실행은 PATH 수정 전에 돌아서 다른 실행과 조건이 같지 않습니다.

## 3. 해석할 때 주의할 점

- **LCB 설정이 실행마다 다릅니다.** 샘플링과 max_tokens 가 다르니 (1-1), 특히 thinking 끔끼리의 비교 (gemma 0.823 vs Qwen 0.724) 는 조심해서 보세요.
  - gemma 끔은 temp 0.2 로 거의 결정적으로 생성했습니다.
  - Qwen 끔은 temp 0.7 에 presence_penalty 1.5 입니다.
- **SWE-bench Pro 는 모델당 51개를 1번씩만 돌렸습니다.** 몇 %p 정도는 흔들릴 수 있습니다. 다만 27개 대 8개는 그 범위를 훨씬 넘습니다.
- **SWE-bench Pro 는 공식 프로토콜이 아닙니다.** 에이전트 컨테이너에서 네트워크와 `/purestorage` 에 접근할 수 있으니 체크포인트끼리 비교하는 용도로만 쓰세요.
- **모델 카드 점수와는 직접 비교하기 어렵습니다.** LCB 문제 구간과 SWE-bench Pro 하네스가 다릅니다.
- **SWE-bench Pro 의 행동 분류는 근사치입니다.** 테스트 실행, 파일 덮어쓰기 등은 에이전트가 실행한 명령을 정규식으로 분류했습니다.
  - 테스트로 센 명령: `pytest`, `go test`, `npm test`, `jest`, `mocha`, `yarn test`, `unittest`, `tox`
  - 직접 만든 재현 스크립트 실행 (`python repro.py` 등) 은 테스트로 세지 않았습니다.
